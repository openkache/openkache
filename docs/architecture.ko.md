# OpenKache 아키텍처

[English](./architecture.md) · **한국어** · [中文](./architecture.zh.md)

OpenKache는 SSD 우선(SSD-first) 캐시 서버입니다. SSD를 인메모리 인덱스 뒤의 스왑 대상으로
다루는 대신, SSD를 주 용량 계층으로 삼고 RAM에는 압축 인덱스만 둡니다. 설계 목표는 단순합니다:
모든 코어가 쓸모 있는 일로 바쁘게 하고, SSD가 순차 대역폭으로 달리게 하는 것.

## Thread-per-core, shared-nothing

전형적인 서버는 요청을 스레드 풀에 넘기고, 그 스레드들은 코어 사이를 옮겨 다닙니다. 옮길 때마다
비용이 듭니다: 락 경합, 뮤텍스 소유권 이전, 컨텍스트 스위치, 그리고 코어 사이를 튕겨 다니는
캐시 라인 — 각각이 동기화와 복사를 강제합니다. 부하가 걸리면 실제 작업이 아니라 이 조율
오버헤드가 병목이 됩니다.

OpenKache는 각 워커를 하나의 코어에 고정합니다. 워커는 자기 데이터를 소유하고 다른 워커와 가변
상태를 공유하지 않으므로, 핫 패스에 락이 없습니다. 이 shared-nothing, thread-per-core 모델은
TigerBeetle·ScyllaDB·Redis가 최신 하드웨어에서 최대 성능을 뽑기 위해 채택한 바로 그 방식입니다.

Redis는 명령을 단 하나의 코어에서 실행합니다. OpenKache는 shared-nothing 원칙을 유지하면서
작업을 코어별로 샤딩하므로, 처리량이 단일 코어 천장에서 멈추지 않고 하드웨어를 따라 확장됩니다.
워커들이 락을 공유하지 않으니 코어를 더해도 경합이 붙지 않습니다.

## 네트워크와 스토리지를 별도 워커로

두 개의 핫 패스는 각자의 코어에서 돕니다:

- **네트워크 워커**는 연결을 받고, 와이어 프로토콜을 파싱하며, 각 요청을 스토리지 메시지로
  바꿉니다.
- **스토리지 워커**는 SSD 데이터 파일과 인메모리 키 인덱스를 소유하고, 조회와 쓰기를
  처리합니다.

둘은 각 방향으로 하나의 **락 프리 SPSC(단일 생산자·단일 소비자) 큐**로 통신합니다. 둘 사이에
공유 가변 상태가 없고 요청 경로에 락이 없으므로, 네트워크 코어의 프로토콜 파싱이 스토리지
코어의 디스크 I/O를 막지 않으며, 그 반대도 마찬가지입니다.

## 스토리지: 키는 RAM에, 값은 SSD에

값은 SSD에 있고, RAM에는 압축 인덱스만 있어 압축된 키를 값이 저장된 세그먼트 오프셋에
매핑합니다. 이렇게 하면 메모리 사용량이 데이터 크기가 아니라 키 개수에 비례하므로, 워킹 셋이
가용 RAM을 훨씬 넘어설 수 있습니다.

### 세그먼트 그룹 쓰기 집계

SSD에 키를 하나씩 쓰는 것은 드라이브를 낭비합니다: 작은 랜덤 쓰기는 순차 한계보다 한참
아래에서 돕니다. 대신 OpenKache는 여러 키의 쓰기를 하나의 순차 **세그먼트 그룹** flush로
묶습니다 — 지하철이 여러 승객을 한 번에 나르지, 각자 따로 차로 가지 않듯이. SSD는 큰 순차
쓰기를 보고 대역폭 한계에 가깝게 돕니다.

Linux에서는 스토리지 워커가 이 I/O를 다이렉트 I/O와 함께 **`io_uring`**으로 제출합니다. 이는
연산마다 드는 시스템 콜 오버헤드를 없애고 커널 페이지 캐시를 우회해, 캐시가 자기 메모리를 직접
관리하게 합니다.

## 하나의 주소에서 듀얼 프로토콜

서버는 같은 숫자 주소를 두 개의 전송으로 노출합니다:

- **RESP over TCP** — Redis 호환 `GET`/`SET`/`DEL`, 그래서 기존 Redis 도구와 클라이언트가
  그대로 동작합니다.
- **OpenKache Gate 0 over QUIC/UDP** — 네이티브 프로토콜로, QUIC 위에서 TLS 1.3을 돌립니다.
  호환성 프론트엔드가 QUIC를 같은 스토리지 엔진에 연결합니다.

## 왜 Rust인가

서버 전체가 Rust로 작성됐습니다. 가비지 컬렉터가 없으니 GC 일시정지가 빠른 경로를 끊을 수
없습니다. 소유권·빌림 모델이 데이터 경쟁을 컴파일 타임에 배제하는데, 이는 설계가 코어 로컬
소유권과 락 프리 큐에 기대기 때문에 특히 중요합니다. 그리고 Rust는 메모리 레이아웃과 시스템
콜에 대한 C 수준 제어를 유지하므로, 위의 하드웨어 중심 설계를 안전성을 포기하지 않고 표현할 수
있습니다.

## 플랫폼 지원

Linux가 주 플랫폼입니다: `io_uring` 네트워크 프론트엔드와 다이렉트 I/O 스토리지 경로가 Linux에
의존하며, 최고 처리량이 나오는 곳도 여기입니다. 포터블 macOS와 Windows/WSL 빌드는
[로드맵](../ROADMAP.ko.md)에 있으며, 최고 처리량보다 개발자 편의와 정확성을 목표로 합니다.
