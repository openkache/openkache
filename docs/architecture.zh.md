# OpenKache 架构

[English](./architecture.md) · [한국어](./architecture.ko.md) · **中文**

OpenKache 是一款 SSD 优先(SSD-first)的缓存服务器。它不把 SSD 当作内存索引背后的交换目标,
而是把 SSD 作为主要容量层,RAM 中只保留一份紧凑索引。设计目标很简单:让每个核心都忙于有用的
工作,并让 SSD 以其顺序带宽运行。

## Thread-per-core,shared-nothing(无共享)

传统服务器把请求交给线程池,而这些线程在核心之间迁移。每次迁移都有代价:锁竞争、互斥量所有权
转移、上下文切换,以及在核心之间弹跳的缓存行。每一样都强制同步与拷贝。负载之下,成为瓶颈的
是这些协调开销,而非实际工作。

OpenKache 把每个工作线程固定到单个核心。工作线程拥有自己的数据,不与其他工作线程共享可变状态,
因此热路径上没有锁。这种 shared-nothing、thread-per-core 模型正是 TigerBeetle、ScyllaDB、
Redis 为从现代硬件榨取最大性能而采用的方式。

Redis 在单一核心上执行命令。OpenKache 保持无共享原则,但将工作按核心分片,因此吞吐量随硬件
扩展,而不是停在单核天花板上。由于工作线程不共享锁,增加核心也不会带来竞争。

## 网络与存储作为独立的工作线程

两条热路径各自运行在自己的核心上:

- **网络工作线程**接受连接、解析线协议,并把每个请求转换为存储消息。
- **存储工作线程**拥有 SSD 数据文件和内存中的键索引,负责查找与写入。

它们在每个方向上通过一条 **无锁 SPSC(单生产者、单消费者)队列** 通信。两者之间没有共享可变
状态,请求路径上也没有锁,因此网络核心上的协议解析绝不会阻塞存储核心上的磁盘 I/O,反之亦然。

## 存储:键在 RAM,值在 SSD

值存放在 SSD 上;RAM 中只有一份紧凑索引,把压缩键映射到其值所存储的段偏移。这使内存占用与键的
数量成正比,而非与数据大小成正比,因此工作集可以远超可用 RAM。

### 段组写入聚合

一次只往 SSD 写一个键是在浪费驱动器:小的随机写远低于其顺序上限。OpenKache 转而把来自多个键的
写入合并成一次顺序的 **段组(segment-group)** 刷写,就像地铁一趟运送许多乘客,而不是每人一辆
车。SSD 看到的是大块顺序写入,从而接近其带宽极限。

在 Linux 上,存储工作线程通过 **`io_uring`** 配合直接 I/O 提交这些 I/O,这消除了每次操作的
系统调用开销,并绕过内核页缓存,让缓存自行管理内存。

## 同一地址上的双协议

服务器在同一个数字地址上暴露两种传输:

- **RESP over TCP:** Redis 兼容的 `GET`/`SET`/`DEL`,因此现有的 Redis 工具和客户端无需改动
  即可工作。
- **OpenKache Gate 0 over QUIC/UDP:** 原生协议,在 QUIC 之上运行 TLS 1.3。一个兼容性前端把
  QUIC 桥接到同一个存储引擎。

## 为什么选择 Rust

整个服务器用 Rust 编写。没有垃圾回收器,因此没有 GC 停顿能打断快路径。所有权与借用模型在编译期
排除数据竞争。这一点尤为重要,正因为该设计依赖核心本地所有权与无锁队列。而且 Rust 保留了对
内存布局与系统调用的 C 级别控制,因此上述以硬件为中心的设计无需放弃安全性即可表达。

## 平台支持

Linux 是主要平台:`io_uring` 网络前端和直接 I/O 存储路径都依赖它,峰值吞吐量也出现在这里。
可移植的 macOS 与 Windows/WSL 构建已列入[路线图](../ROADMAP.zh.md),以开发者体验和正确性为
目标,而非峰值吞吐量。
